# Releases

Related: [roadmap](roadmap.md) · [dependencies](dependencies.md) · [CHANGELOG](../CHANGELOG.md)

## 1. Versioning

The project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html),
with the usual pre-1.0 allowance: a **minor** release may add sites, flags and
extractors; a **patch** release only fixes defects.

What counts as breaking here is not the command line but the *contract*:

| Change | Version |
| --- | --- |
| adding a site, a flag, a container, a JSON field | minor |
| refusing something that used to work (a site changed, a format moved behind a check) | minor — it never makes the tool write something worse |
| changing the default quality, the default name, or the meaning of an exit code | **major** |
| changing the JSON schema meaning | **major** (the `schema` field exists so this can be detected) |
| removing a site | **major** |

`tafas --version` prints the crate version. The binary has no self-update
mechanism, checks for nothing and downloads nothing except the URL you gave it.

**Nothing was tagged until the whole roadmap was done**, and then one archive
carried all of it: **0.2.0, 2026-11-08**, with v0.2 through v0.5 of the
[roadmap](roadmap.md). This is deliberate: a tag is a promise about an archive
that cannot be edited afterwards, and an item that is still being built is not a
promise yet. From here on, an item that lands is a minor release of its own when
the owner says so; `main` is ahead of the last archive as soon as that happens,
and `cargo install --git https://github.com/RUdolf1517/tafas` is how a reader
gets what is not released.

**0.2.0 is not signed, and one of its packages is not either.** Both need a key
this repository does not hold, and both say so rather than pretending: the
publish job signs when `MINISIGN_SECRET_KEY` and `packaging/minisign.pub` exist,
and the Alpine `.apk` installs with `--allow-untrusted` ([§3](#3-channels)).
Everything else — `SHA256SUMS`, the SBOM, the reproducible build — is in the
archive as described below.

## 2. What a release contains

| Artifact | Target | Notes |
| --- | --- | --- |
| `tafas-x86_64-unknown-linux-musl.tar.gz` | `x86_64-unknown-linux-musl` | statically linked; no libc dependency |
| `tafas-aarch64-unknown-linux-musl.tar.gz` | `aarch64-unknown-linux-musl` | ARM64 servers; crossed with `cargo-zigbuild`, because `ring` has C to compile |
| `tafas-x86_64-apple-darwin.tar.gz` | `x86_64-apple-darwin` | Intel Macs |
| `tafas-aarch64-apple-darwin.tar.gz` | `aarch64-apple-darwin` | Apple silicon |
| `tafas-x86_64-pc-windows-msvc.zip` | `x86_64-pc-windows-msvc` | Windows x64 |
| `tafas_amd64.deb`, `tafas_arm64.deb` | Debian, Ubuntu | the static musl binary; no dependencies declared |
| `tafas.x86_64.rpm`, `tafas.aarch64.rpm` | Fedora, RHEL | the same static binary |
| `tafas-X.Y.Z-x86_64.apk`, `tafas-X.Y.Z-aarch64.apk` | Alpine | the same static binary, unsigned: `apk` asks for `--allow-untrusted` |
| `tafas-channels-X.Y.Z.tar.gz` | — | `PKGBUILD`/`.SRCINFO` for the AUR, a Scoop manifest and a `flake.nix`, all rendered from the release's `SHA256SUMS` |
| `install.ps1` | — | the per-user Windows installer, published as an asset so its own bytes are in `SHA256SUMS` |
| `tafas-winget-local-manifests-vX.Y.Z.zip` | — | winget manifests for the exact Windows ZIP; local installs only |
| `tafas-release-X.Y.Z.spdx.json` | — | what is in the archives, built from the lock file the build used |
| `SHA256SUMS` | — | one line per artifact, including the installer and the SBOM |
| `*.minisig` | — | one signature per artifact, plus `SHA256SUMS.minisig`, when the signing key is present |
| source archives | — | generated by GitHub from the tag |

Every POSIX archive carries `tafas`, `man/tafas.1`, `completions/` (bash, zsh,
fish) and `LICENSE`. The packages install the manual page and the completions,
so `man tafas` works after `apt install`, `dnf install` or `brew install`.

The Windows ZIP carries exactly two entries, `tafas.exe` and `LICENSE`, and both
consumers of it — `install.ps1` and the winget manifest generator — refuse an
archive with anything else rather than unpacking a surprise. A Windows archive
carries no manual page or completions: there is no `man` to read them with, and a
`tafas.exe --completions powershell` covers the shell that exists.

The SBOM is published once, as `tafas-release-X.Y.Z.spdx.json`, rather than
copied into five archives: it describes the release, not the platform, and five
copies of one document invite the reader to wonder which is current.

Asset names are Rust target triples and carry no version. That is deliberate: it
makes `https://github.com/RUdolf1517/tafas/releases/latest/download/<asset>` a
stable URL, which is what `install.sh` downloads from.

## 3. Channels

| Channel | Platforms | Command |
| --- | --- | --- |
| shell script | Linux x86_64/aarch64, macOS arm64/Intel | `curl -fsSL https://raw.githubusercontent.com/RUdolf1517/tafas/main/install.sh \| sh` |
| Homebrew | macOS arm64, Linux x86_64 | `brew tap RUdolf1517/tafas https://github.com/RUdolf1517/tafas` then `brew install RUdolf1517/tafas/tafas` |
| apt | Debian, Ubuntu (amd64, arm64) | download `tafas_amd64.deb`, then `sudo apt install ./tafas_amd64.deb` |
| dnf | Fedora, RHEL (x86_64, aarch64) | download `tafas.x86_64.rpm`, then `sudo dnf install ./tafas.x86_64.rpm` |
| apk | Alpine (x86_64, aarch64) | download `tafas-X.Y.Z-x86_64.apk`, then `doas apk add --allow-untrusted ./tafas-X.Y.Z-x86_64.apk` |
| AUR | Arch (x86_64, aarch64) | `PKGBUILD` from `tafas-channels-X.Y.Z.tar.gz`, then `makepkg -si` |
| Scoop | Windows 10/11 x64 | `tafas.json` from `tafas-channels-X.Y.Z.tar.gz` into a bucket, then `scoop install tafas` |
| Nix | any NixOS or Nix on Linux/macOS | `flake.nix` from `tafas-channels-X.Y.Z.tar.gz`, then `nix profile install .` |
| cargo | anything with Rust 1.82+ | `cargo install --git https://github.com/RUdolf1517/tafas --tag v0.2.1` |
| PowerShell | Windows 10/11 x64 | download `install.ps1` from the release, then `powershell -NoProfile -ExecutionPolicy Bypass -File .\install.ps1` |
| winget (local manifest) | Windows 10/11 x64 | unpack `tafas-winget-local-manifests-vX.Y.Z.zip`, then `winget install --manifest <version>` |
| archive | everything else | unpack, put `tafas` on `PATH` |

`apk` is the only channel that asks the user for `--allow-untrusted`. The package
is built by `packaging/apk.py` from the same static tarball the other packages
are built from, and it is **not signed**: signing needs an Alpine private key,
which is a secret this repository does not hold — the same restriction, and the
same honesty, as `packaging/minisign.pub` in §7. It is the v2 package format,
which every apk-tools since 2.0 reads; `apk mkpkg` would have written v3, which
only Alpine 3.23 and newer can install, and the audience for a package installed
by path is mostly the older branches. The AUR,
Scoop and flake files are rendered from the release's `SHA256SUMS` by
`packaging/channels.py`, so each hash in them is the hash of an archive that
exists; none of the three is checked in, because a file that repeats the hash of
an archive is stale the moment the next archive is built.

`install.sh` prefers the prebuilt binary and falls back to a source build only
when no asset exists for the platform. A download, checksum, unpacking or
version error is fatal and never reported as an absent asset.

**It verifies what it downloads.** The archive is checked against the release's
`SHA256SUMS` before it is unpacked. A mismatch, a missing checksum file, a
network error or a corrupt archive aborts the install; none of them falls back to
a source build that would hide the mismatch.

`TAFAS_VERSION`, `TAFAS_INSTALL_DIR`, `TAFAS_REPO` and `TAFAS_BASE_URL` adjust
what it does. `TAFAS_BASE_URL` points at a mirror — the layout is
`<base>/<asset>` and `<base>/SHA256SUMS`, and the checksum check is not optional
there either.

### Windows: a per-user installer, not an MSI

`packaging/windows/install.ps1` is the Windows channel. It installs for the
current user only, into `%LOCALAPPDATA%\Programs\tafas` (or `-InstallRoot`,
which must be inside the user profile), and it never asks for elevation. There is
no MSI, no MSIX and no machine-wide installer: a tool that writes to another
profile should be a deliberate act, and `tafas.exe` is a single static binary, so
one directory and one `PATH` entry is the whole of it.

What it checks before it writes anything:

| Check | Refusal |
| --- | --- |
| the release is x64 | any other `PROCESSOR_ARCHITECTURE` |
| `SHA256SUMS` parses and names this archive exactly | a malformed, duplicated or foreign checksum file |
| the archive's SHA-256 matches | any mismatch, and the previous install survives |
| the ZIP holds exactly `tafas.exe` and `LICENSE` | an archive with extra or missing entries |
| `tafas.exe --version` equals the tag | a binary that does not answer for that version |
| the target directory is the installer's own | a directory without `.tafas-installer.json`, or one holding unmanaged files |

`-Uninstall` removes the files listed in the marker and the `PATH` entry the
marker says it added, and nothing else: a file in the same directory that the
installer did not write stays. Replacement is a directory rename with a backup
beside it, so a failure at any step puts the previous version back, and a locked
`tafas.exe` is reported instead of half-replaced. `-Version vX.Y.Z` pins a
release; the default resolves `releases/latest` through the GitHub API, where
`TAFAS_GITHUB_TOKEN` may be set to a read-only token to avoid anonymous rate
limits.

The winget manifests are generated at release time from the bytes of the ZIP that
shipped (`packaging/winget/generate.py`), so the `InstallerSha256` they carry is
the hash of the release asset, not of a rebuild. They are attached as a bundle and
**never submitted to `winget-pkgs`**: installing from them is
`winget install --manifest <directory>`. A community-repository entry is a
reviewed publication with its own cadence, and claiming one here would be a
promise this repository does not keep.

## 4. How a release is cut

These steps were run once, for 0.2.0, which carried the whole roadmap
([§1](#1-versioning)); a later release runs the same steps for its own version.

1. `CHANGELOG.md` gets its section, `Cargo.toml` its version.
2. The version is committed to `main` with the tag that will carry it.
3. `git tag vX.Y.Z && git push origin vX.Y.Z`.
4. The release workflow builds the five targets, packages them with the manual
   page and the completions, builds the `.deb`/`.rpm` from the Linux tarball
   with `nfpm` and the `.apk` from the same tarball with `packaging/apk.py`, copies
   `install.ps1` into the assets, renders the winget manifests from the Windows
   ZIP, writes the SBOM, writes `SHA256SUMS`, renders the AUR, Scoop and flake
   files from those checksums, signs every file when the key is present, and
   attaches everything to the release.
5. The Homebrew formula gets the new version and the hashes from
   `SHA256SUMS`; this is a follow-up commit, and it is the only hand edit in the
   process.
6. `cargo install` works from the tag without any additional publication step.

Nothing is built on a developer machine. The workflow is the only place a
shipped binary is produced, which is what makes "the archive contains what the
tag contains" a property rather than a hope.

The publish job needs three tools beyond Rust and the shell: `nfpm` (Go) for the
`.deb`/`.rpm`, `python3` for the `.apk`, the winget manifests, the
AUR/Scoop/flake files and the SBOM, and `minisign` only when the signing key is
set. Nothing in the publish job needs Docker: the `.apk` is a format, not a
toolchain, and writing it in Python removed the container, the Alpine image tag
and a class of "the image moved and the command is gone" failure. Two things
stay human, and both for the same reason — a key this
repository does not hold: the AUR package is pushed with an AUR key, and the
`.apk` is unsigned. None is needed by anyone who installs a
release; on Windows the installer needs only PowerShell, which Windows already
has.

## 5. Support

Security reports are investigated against the latest release and `main`; see
[SECURITY.md](../SECURITY.md). Backports to older releases are not guaranteed.
A site changing its pages is a *defect*, not a vulnerability — it gets a patch
release, and the refusal it produces already names itself, which is what makes
the report actionable.

## Reproducibility, signatures and the SBOM

The release build is a function of the commit and nothing else:

| What | How |
| --- | --- |
| the clock | `SOURCE_DATE_EPOCH` is the commit's own time (`git log -1 --format=%ct`), and `Cargo.toml` carries a fixed `version` |
| the directories | `RUSTFLAGS=--remap-path-prefix=<runner>=/build --remap-path-prefix=<cargo home>=/cargo`, so a panic message names `/build/src/main.rs` on every machine |
| the build cache | `CARGO_INCREMENTAL=0`; every artifact is built from scratch |
| the dependencies | `--locked`, so the release is the `Cargo.lock` in the tag |

What a reader does with that:

```sh
sha256sum --check SHA256SUMS                       # the file matches the release
minisign -Vm SHA256SUMS -p minisign.pub -x SHA256SUMS.minisig   # the release is ours
minisign -Vm tafas-x86_64-unknown-linux-musl.tar.gz \
  -p minisign.pub -x tafas-x86_64-unknown-linux-musl.tar.gz.minisig   # or one file
python3 -m json.tool tafas-release-0.4.0.spdx.json > /dev/null   # and what is in it
```

Signatures exist when the `MINISIGN_SECRET_KEY` secret is set, and then every
artifact has one: `tafas-<target>.tar.gz.minisig` beside the archive,
`SHA256SUMS.minisig` for the collection, and a copy of `minisign.pub` in the
release so nobody has to go looking for the key. `packaging/sign.sh` writes them
and verifies each against the public key before the job uploads anything. The key
is created without a passphrase — minisign cannot read one from a pipe — and kept
in the secret store; the public half is committed as `packaging/minisign.pub`.
The publish job refuses to sign when that file is missing, because a signature
whose key nobody has is a document, not a proof.

`tafas-release-X.Y.Z.spdx.json` is SPDX 2.3, built from `Cargo.lock` by
`packaging/sbom.py`: one package per crate with its version, its SHA-256 from the
lock file and a `pkg:cargo/` purl. No cargo, no network, no dependencies: the
lock file is read as the TOML it is. Two builds of one commit produce the same
document, byte for byte, because the packages are sorted and the timestamp comes
from `SOURCE_DATE_EPOCH`.

The declared floor, `rust-version = "1.82"`, is a job of its own in
[`ci.yml`](../.github/workflows/ci.yml): `cargo build --locked --all-targets` at
that exact version, on every push. A dependency that raises the floor fails the
build there, which is the only place it can fail quietly otherwise.
